## 3. สถาปัตยกรรมและเทคโนโลยี

### 3.1 Stack

| ชั้น | ต้นแบบใช้ | หมายเหตุ |
|---|---|---|
| ภาษา | HTML5 · CSS custom properties · JS ES2022 modules | ไม่มี TypeScript / JSX / bundler ตอน dev |
| UI | vanilla DOM — helper `h(tag, attrs, ...kids)`, `$()`, `$$()` | ทุกโมดูล UI = `mountX(root, cfg)` คืน object ควบคุม |
| State | อยู่ใน closure ของแต่ละโมดูล · มี singleton `cart` + `localStorage` | ไม่มี store กลาง |
| 3D | three.js r170 (vendored ห้ามแก้) · procedural ทั้งหมด | engine = `createX(container, opts)` มี `dispose()` |
| ฟอนต์ | self-host woff2: IBM Plex Sans Thai (เนื้อหา) · Anuphan (หัวข้อ) · IBM Plex Mono (ตัวเลข/ป้าย) | ห้ามโหลดจาก CDN |
| Build | `build.py` (Python 3.11) + esbuild 0.28.2 | ได้ 3 แบบ: `dist/site` (แยกไฟล์ ขึ้นเว็บ) · `dist/offline` (ไฟล์เดียว ~2.7 MB) · `dist/art` (Claude Artifacts) |
| Hosting | GitHub Pages (Actions) | หน้าแรกโหลด ~590 KB · ใช้ได้ (4G จำลอง) ~5 วินาที |
| ทดสอบ | Playwright 1.56 (Chromium + swiftshader) · axe-core 4.13 | CI รันเฉพาะเทสต์ที่ไม่ต้องใช้ browser |
| หลังบ้าน | Google Apps Script (Sheet แท็บ: ใบเสนอราคา · ติดต่อ · ความเห็น · งานจอง · คิว) + Drive (รูปหน้างาน) + อีเมล + LINE Messaging API | `BACKEND_URL` ยังว่าง |

### 3.2 วิธีประกอบหน้า

```
a.html / b.html / c.html  ── <script type="module"> ตัวเดียว
   await loadData()  → อ่าน Pricebook + สมุดที่อยู่ แปลงตามกฎธุรกิจตอนโหลด
   await loadMedia() → รูปสินค้า (ถ้าไม่มี ใช้ภาพเรนเดอร์ 3D)
   mountX(...) ทีละ section  (catalog, booking, studio, jobguide, enterprise …)
   mountSite({views})       ← ท้ายสุด: แบ่ง section ยาว ๆ เป็น 6 "หน้า" + เมนู + เส้นทางลูกค้า
```

- **ชั้น domain แยกจาก UI ชัดเจน**: `sbp-core.js` (ราคา, VAT, โซน, ค่าเดินทาง, สัญญา, BTU), `studio-model.js`, `roomplan.js`, `rates.js`, `acdiag.js` เป็นตรรกะล้วน ไม่มี DOM → เทสต์ด้วย node ได้
- **3D โหลดแบบ lazy** เมื่อเลื่อนถึง (`IntersectionObserver` + `whenQuiet`) · คุมงบ WebGL ≤ 3 context ต่อหน้า (`gl-pool.js`) · หยุด render เมื่อออกจอ · เคารพ `prefers-reduced-motion` · มีข้อความสำรองเมื่อเปิด WebGL ไม่ได้
- **แหล่งข้อมูลเดียว (single source)**: ข้อมูลบริษัท = `COMPANY` · ขั้นตอนช่าง = `services.js` · ราคา = Pricebook (+ `rates.js`) · ตัวเลขใน FAQ ดึงจากค่าคงที่เดียวกับเครื่องคิดเงิน

## 4. โครงข้อมูลเว็บ (Information Architecture)

### 4.1 6 "หน้า" ตามการตัดสินใจของลูกค้า (`site.js`)

ทุกแบบมี 6 หน้าเหมือนกัน แต่เรียง section ต่างกัน (B เรียงเมนูเป็น หน้าแรก → องค์กร → บริการ → ซื้อ → ความรู้ → ติดต่อ และใส่เลข `00–05`)

| หน้า | แบบ A | แบบ B | แบบ C |
|---|---|---|---|
| หน้าแรก | hero · book · start · flow · services | hero · book · start · coverage · flow | top · book · start · coverage · flow |
| ซื้อแอร์ | catalog · tradein · studio · fit | catalog · tradein · fit · studio | catalog · tradein · room · fit |
| ล้าง·ติดตั้ง·ซ่อม | cleanflow · symptoms · standards · prices · quality · story · inside | cleanflow · symptoms · howto · standards · prices · quality | cleanflow · symptoms · howto · standards · prices · quality |
| สำหรับองค์กร | enterprise · b2b | enterprise · b2b | enterprise · b2b |
| ความรู้·ลองเอง | learn · howto | learn · inside | journey · learn |
| ติดต่อเรา | about · area · faq · quote | about · area · faq · quote | about · area · faq · quote |

> ทั้งหมดอยู่ใน **ไฟล์ HTML เดียวต่อแบบ** — "หน้า" คือการซ่อน/แสดง section ด้วย JS และใช้ `#hash` เป็นลิงก์ ไม่ใช่ URL แยก

### 4.2 เส้นทางลูกค้า (Guided journeys) — หน้าแรก "วันนี้ต้องการอะไร"

| เส้นทาง | ขั้นตอนที่ระบบพาไป |
|---|---|
| ล้างแอร์ | จองล้าง (เลือกแอร์ วิธีล้าง พื้นที่) → ดูทีมช่างล้างทีละขั้น → ส่งคำขอ |
| ซื้อแอร์ใหม่ + ติดตั้ง | หาขนาด BTU ในห้องจำลอง → เลือกรุ่น + แพ็กเกจติดตั้ง → ลองวางในห้อง → ส่งใบเสนอราคา |
| ติดตั้ง / ย้ายแอร์ | ขั้นตอนติดตั้ง → วัสดุในแพ็กเกจ → ราคาติดตั้งตามขนาด → จองคิว/ขอสำรวจ |
| แอร์มีปัญหา / ซ่อม | เช็กอาการ → ขั้นตอนตรวจซ่อม → ค่าตรวจ/ค่าซ่อม → จองช่างพร้อมแนบรูป |
| เทิร์นแอร์เก่า | เทียบซ่อม vs เปลี่ยน → เลือกเครื่องใหม่ → ขอประเมินมูลค่าเทิร์น |
| องค์กร / สัญญารายปี | เลือกประเภทองค์กร → ประเมินงบทั้งปี → มาตรฐานงาน → พื้นที่ → ส่งคำขอ |

ระบบแสดง "ขั้นที่ n จาก N" (แถบตัวเลขด้านซ้าย) จำความคืบหน้าใน `localStorage` และมีการ์ด "ขั้นต่อไป" ท้ายทุกหน้า

### 4.3 ส่วนประกอบที่อยู่ทุกหน้า

- Header: โลโก้ SP · เมนู 6 หน้า · ค้นหา **Ctrl/⌘ K** (รุ่นแอร์, บริการ, หัวข้อ, คำสั่งด่วน) · สลับแบบ A/B/C · ปุ่ม **ใบเสนอราคา (n)**
- ปุ่มลอย (คอม): "ถามอาการแอร์" (ผู้ช่วยอัตโนมัติ) + "แชท LINE" · แถบล่าง (มือถือ): เมนู · ติดต่อ · LINE · ใบเสนอราคา
- ใบเสนอราคา (drawer): รายการ · พื้นที่ → ค่าเดินทาง · ยอดก่อน VAT / VAT / รวม · ส่งคำขอ / คัดลอกไป LINE
- Footer: ข้อมูลบริษัทจาก `COMPANY` · ฟอร์มความเห็น (beta)

### 8.2 รูปแบบ token ที่ควรยืมมาใช้
- token ต่อแบบใน `:root` + **alias กลาง `--s-*`** (`--s-card --s-ink --s-line --s-accent --s-on-accent --s-ok --s-warn --s-bad --s-r --s-mono` …) ให้คอมโพเนนต์ร่วมอ้างได้ทุกธีม
- dark mode: `@media (prefers-color-scheme: dark)` + `:root[data-theme="dark"]`
- motion token กลาง (ห้ามตั้ง easing/เงาเองต่อจุด)
- CSS prefix ต่อโมดูล (`s-` `st-` `sv-` `hw-` `ts-` …)

### 8.3 กฎ UX / Accessibility ที่ต้นแบบวางไว้
- WCAG 2.2 AA: contrast ≥ 4.5:1 · หัวข้อไม่ข้ามระดับ · `<main>` เดียว · canvas 3D `aria-hidden` แต่มีข้อความทางเลือกครบ
- ปุ่ม/ช่องกรอกบนจอสัมผัสสูง ≥ 44 px · ไม่มีเลื่อนแนวนอนทั้งหน้า (ทดสอบ 1366×900 และ 390×844) · `safe-area-inset` สำหรับ iPhone
- ไม่ใช้เอฟเฟกต์ลอยขึ้นทีละ section · ไม่มี "→" ท้ายปุ่ม · ป้ายควบคุมเป็นภาษาไทยที่ลูกค้าเข้าใจ
- ภาษาไทย: ห้าม letter-spacing ติดลบ / line-height ต่ำ (body `16px/1.7`)

- **CI**: ทุก PR รันเทสต์เร็ว (Apps Script parse + public functions, คัดกรองอาการ, เทิร์น, อัตรา, องค์กร) · deploy Pages ต้องผ่าน checks ก่อน · build เขียน `version.json` (sha/ref/เวลา)
- **บันทึกการเปลี่ยนแปลง** เป็น Rev.xx พร้อมคำสั่งเจ้าของในหัวไฟล์ทุกโมดูล — ตามรอยได้ดีมาก แต่ทำให้คอมเมนต์ยาวและปนภาษา
- **เครื่องมือ AI**: ใช้ Claude Code + skills ออกแบบ (UI UX Pro Max ฯลฯ) + MCP server ฐานข้อมูลดีไซน์

## 10. ประเมินแบบตรงไปตรงมา

### 10.1 สิ่งที่ควรยืม (จุดแข็ง)
1. **แยก domain logic ออกจาก UI** — สูตรราคา/VAT/ค่าเดินทาง/สัญญา เป็นฟังก์ชันล้วน เทสต์ได้
2. **แหล่งข้อมูลเดียว** สำหรับราคา ข้อมูลบริษัท และขั้นตอนงาน — ตัวเลขทุกจุดบนเว็บตรงกันเสมอ
3. **IA ตามการตัดสินใจของลูกค้า** — 6 หน้า + เส้นทางนำทาง + การ์ดขั้นต่อไป
4. **จองล้าง 3 ขั้นพร้อมราคาสด** — คำนวณแบบเดียวกับใบเสนอราคา ลดคำถามซ้ำ
5. **UX ที่ซื่อตรง** — ป้าย "แบบจำลอง", ไม่แกล้งว่าส่งแล้ว, ไม่โชว์คิวว่างปลอม, สแกนคำต้องห้ามอัตโนมัติ
6. **ระบบ token + alias** ที่รองรับหลายธีม และ motion token กลาง
7. **วินัยด้านประสิทธิภาพ** — lazy 3D, งบ WebGL, build แยกไฟล์ cache ได้, ฟอนต์ self-host
8. **CI gate ก่อน deploy** + เทสต์ไม่มี overflow / textscan

### 10.2 สิ่งที่ไม่ควรทำตาม (จุดอ่อน / บทเรียน)
1. **ไม่มี URL จริงต่อหน้า** — ทุกอย่างอยู่ใน HTML ไฟล์เดียวต่อแบบ สลับ "หน้า" ด้วย JS → SEO อ่อน หน้าสินค้า 705 รุ่นไม่มี URL ของตัวเอง แชร์ลิงก์ได้แค่ `#hash`
2. **ทำ 3 ดีไซน์พร้อมกันจนถึง Rev.28** โดยยังไม่เลือก → ทุกฟีเจอร์ต้องจูน 3 รอบ (CSS/markup ×3)
3. **เนื้อหาแน่นเกิน** — หนึ่งหน้ามี 5–7 section ที่แต่ละ section เป็นเครื่องมือใหญ่ ข้อความยาวมาก ลูกค้าทั่วไปอาจหลง
4. **3D เยอะมาก (~25 โมดูล)** และยังไม่เคยทดสอบบนมือถือจริง (ทดสอบแค่ headless) — เสี่ยงช้า/ร้อน/กินแบต
5. **โค้ดอ่านยาก** — one-liner ยาว ไม่มี type ไม่มี framework โมดูลใหญ่ (เช่น `jobscene3d.js` 813 บรรทัดแน่น) → ทีมใหม่รับช่วงยาก
6. **เอกสารใหญ่มาก (รวม ~500 KB) และขัดกันเอง** เช่น
   - กฎแสดงราคา: เอกสารบางจุดยังเขียน "แสดงราคารวม VAT เป็นหลัก" แต่โค้ด (Rev.16) แสดง **ก่อน VAT ทุกจุด**
   - ค่าเดินทาง: ตัวอย่างโค้ดใน `CLAUDE.md` §4.3 ยังเป็นกฎเก่า (Z1/Z2/Z3 300/800/1,500) แต่โค้ดจริงเป็น 300 + 10/กม.
   - ที่อยู่: "พระราม 2 ซอย 31" vs "593 ถ.พระราม 2" · hosting: "Claude Artifacts" vs GitHub Pages · ตาราง token สีใน §5.1 เป็นค่าก่อน Rev.20
   - หัว `HANDOFF.md` เขียน "สถานะ Rev.14" แต่เนื้อหาถึง Rev.28
7. **ไฟล์ค้าง** — `index.html` (275 KB), `hub*.html`, `test-*.html` หลายไฟล์ปนอยู่ในโฟลเดอร์หลัก
8. **ท่อข้อมูลราคาไม่ครบ** — สคริปต์ Excel → JSON ไม่อยู่ใน repo · หลังบ้านเขียนเสร็จแต่ยังไม่ deploy · ฟอร์มตอนนี้ผ่าน FormSubmit (เซิร์ฟเวอร์ต่างประเทศ — ต้องคิดเรื่อง PDPA)
9. **ยังไม่มีรูปจริง** — สินค้าใช้ภาพเรนเดอร์ 3D กลาง ๆ · ยังไม่มีภาพทีม/หน้างานจริง

## 11. แนวทาง "ถอดแล้วสร้างในแบบฉบับของเรา" (ข้อเสนอ — รอยืนยัน)

แบ่งต้นแบบเป็น 3 ชั้น แล้วตัดสินใจทีละชั้น:

| ชั้น | สิ่งที่อยู่ในชั้นนี้ | แนวทางที่เสนอ |
|---|---|---|
| **เนื้อหาและกฎ** | ราคา Pricebook · กฎธุรกิจ §7 · ขั้นตอนงาน · ข้อความความรู้ · FAQ | **นำมาใช้ต่อ** (ถ้าเป็นธุรกิจเดียวกัน) — ย้ายเป็นไฟล์ข้อมูล/โมดูลที่มี type + unit test |
| **โครงและประสบการณ์** | IA 6 หน้า · เส้นทางลูกค้า · จองล้าง 3 ขั้น · ใบเสนอราคา · คัดกรองอาการ | **คงแนวคิด แต่ทำใหม่ให้เบาและชัดกว่า** — URL จริงต่อหน้า, ลดจำนวน section ต่อหน้า, เน้น 1 งานหลักต่อหน้า |
| **ภาพลักษณ์และเทคนิค** | สี ฟอนต์ เลย์เอาต์ 3D animation · สถาปัตยกรรมโค้ด | **ออกแบบใหม่เป็นสไตล์ของเราแบบเดียว** (ไม่ทำ 3 แบบ) · เลือก 3D เฉพาะจุดที่ช่วยขายจริง 2–3 จุด |

ลำดับงานที่เสนอ:
1. **Phase 0 — ตัดสินใจ** (คำถามด้านล่าง)
2. **Phase 1 — ฐานราก**: โครง repo · design tokens ของเรา · sitemap + routes · content model · ย้ายตรรกะราคาเป็นโมดูลมีเทสต์
3. **Phase 2 — หน้าหลัก + การขาย**: หน้าแรก + จองล้าง · ราคาค่าบริการ · catalog + หน้าสินค้า (URL ต่อรุ่น) · ใบเสนอราคา
4. **Phase 3 — ฟีเจอร์เด่น**: เลือกจาก ห้องจำลอง/หา BTU · ทีมช่างทีละขั้น · คัดกรองอาการ · หน้าองค์กร + ตัวคำนวณสัญญา
5. **Phase 4 — หลังบ้าน**: ฟอร์ม/ใบจอง → Sheet หรือฐานข้อมูล · แจ้งเตือน LINE/อีเมล · analytics
6. **Phase 5 — QA & เปิดใช้**: เทสต์อัตโนมัติ · a11y · ความเร็วบนมือถือจริง · deploy

### เรื่องที่ต้องตัดสินใจก่อนเริ่ม
1. เว็บใหม่เป็นของ **ธุรกิจเดียวกัน (SBP AirCare / สหบูรพากรุ๊ป)** หรือแบรนด์/ธุรกิจอื่น? (กำหนดว่าใช้ราคา โลโก้ ข้อมูลบริษัทต่อได้ไหม)
2. "แบบฉบับของเรา" — มีสี/โลโก้/เว็บอ้างอิงที่ชอบไหม หรือให้เสนอแนวดีไซน์ใหม่ก่อน?
3. เทคโนโลยี — ทำแบบ vanilla เหมือนต้นแบบ หรือขึ้นโครงใหม่ (เช่น Next.js + TypeScript ตามที่เอกสารต้นแบบแนะนำไว้สำหรับเวอร์ชันจริง)?
4. ขอบเขตรอบแรก — เริ่มจากหน้าไหน/ฟีเจอร์ไหน และต้องการ 3D มากน้อยแค่ไหน?
